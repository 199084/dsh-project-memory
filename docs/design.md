# 设计说明

本文说明 `dsh-project-memory` 为什么这样设计、数据怎么流动，以及它在哪些地方**故意**留白。实现细节以 [index.mjs](../index.mjs) 为准。

## 1. 出发点

Agent 记忆的主流做法是让模型自己决定记什么：从会话中提炼事实、写入向量库或数据库、下次按相似度召回。这套方案在演示里很好看，在长期项目里会积累三种代价：

| 代价 | 表现 |
| --- | --- |
| 记忆幻觉 | 一次推理的中间结论被写成「事实」，随后被反复当真 |
| 错误扩散 | 错误进入记忆库后会被后续每次注入放大，且难以定位写入点 |
| 无法回溯 | 记忆没有 diff、没有 blame、没有回滚，Review 无从下手 |

本插件的判断是：**值得长期保留的不是模型的想法，而是经得起 Review 的项目决策。** 决策的载体不需要数据库，一个跟着代码走 Git 的 Markdown 文件就够。

## 2. 四条原则

1. **人类掌控**：`MEMORY.md` 是唯一确定性事实来源，代码中不存在任何写入它的路径。
2. **随仓库版本化**：记忆与代码同仓，提交、合并、Review 流程完全复用。
3. **显式来源标记**：注入带路径与修改时间，检索带行号。
4. **提案式更新**：模型只能产出候选条目，人的审阅是写入的唯一入口。

## 3. 数据流

插件有且只有三条数据通路。

### 3.1 注入通路（读 `MEMORY.md`）

```text
会话构建系统提示词
  └─ systemPrompt.context({ name: 'project-memory', order: -20 })
       └─ 取 agent.session.header.cwd 作为工作区
            └─ 校验 memoryPath 未逃出工作区
                 └─ readFileSync + slice(0, maxChars)
                      └─ 拼接来源、修改时间、截断提示后注入
```

要点：

- `text` 是一个**函数**而不是常量，每次构建提示词时重新读盘，因此编辑 `MEMORY.md` 立即生效，无需重启会话。
- 文件不存在（`ENOENT`）时返回空字符串，注入为空，不打扰会话。
- `order: -20` 让记忆排在其它运行时上下文之前，靠近系统提示词的稳定区域。

### 3.2 检索通路（`project_memory` 工具）

```text
模型调用 project_memory(query)
  └─ 取 exec.agent.session.header.cwd
       └─ 读取记忆文件
            └─ query 按 [^\p{L}\p{N}_-]+ 切分为词元，丢弃长度 ≤ 1 的词元
                 └─ 逐行统计命中词元数 → 按命中数降序、行号升序排序
                      └─ 取前 maxMatches 行 → 再按行号升序还原
                           └─ 输出「行号: 原文」形式摘录
```

要点：

- 匹配是**大小写不敏感的词面子串命中**，没有 embedding、没有同义词扩展。
- 若查询里没有有效词元（例如只有单个汉字或标点），函数直接返回记忆全文——这是一条兜底分支，调用方应当用具体名词提问。
- 工具输出包含 `found`、`path`、`excerpt`、`truncated`、`updatedAt`，便于模型自证来源。

### 3.3 候选通路（`lazyMode`）

```text
agent/turn-stopping 事件
  └─ 取会话事件流中 seq 大于上次扫描位置的部分（新增量）
       └─ 仅保留 type = 'user/message' 且 data.source.kind = 'user' 的事件
            └─ 文本空白折叠为单空格、截断到 500 字符
                 └─ 与候选文件中已有条目去重
                      └─ 受 maxCandidates 条数与 maxCandidateChars 字符数上限约束
                           └─ 追加为「- [ ] 条目」
```

要点：

- **只采用户消息**。插件注入的运行时上下文（`source.kind` 为 `plugin`）与模型输出都被排除，避免记忆自我污染。
- 候选是原文的机械截取，不是模型总结——总结属于人的工作。
- 扫描位置按会话 id 记录（`scanned` Map），每个会话只扫描新增事件，不会重复写入。
- 上限触发时**静默跳过**，不新增也不报错。

## 4. 代码结构

| 位置 | 职责 |
| --- | --- |
| `name` / `inject` | 声明插件名与依赖的服务（`tools`、`systemPrompt`） |
| `Config` | 用 schemastery 定义 7 个配置项及其取值范围 |
| `workspaceOf` | 从 Cordis 上下文取会话工作目录 |
| `memoryPath` | 解析并校验路径必须落在工作区内，否则抛错 |
| `readMemory` / `readMemorySync` | 读取、截断、取修改时间；`ENOENT` 视为「没有记忆」 |
| `scoreLine` / `relevantExcerpt` | 关键词打分与带行号摘录 |
| `textOf` / `candidateFrom` | 从消息内容块提取纯文本并规范化为候选 |
| `candidateCount` / `appendCandidates` | 上限判断、去重与追加 |
| `apply` | 挂载注入器与工具，注册 `agent/turn-stopping` 监听 |

## 5. 关键取舍

**为什么不用向量检索？** 项目记忆的量级通常在几十行到几百行，检索目标不是「相似语义」而是「确定事实」。词面命中配合行号引用，可解释、可复现、可调试；向量召回在这类场景里换来的是不确定性。

**为什么整段注入而不是按需检索？** 注入解决「模型不知道要问什么」的问题——它连自己缺哪块上下文都不清楚。检索解决「知道要问什么」的问题。两者互补，因此注入保底、检索增效。

**为什么候选不交给模型生成？** 一旦允许模型总结，幻觉就从「记忆库」前移到「候选生成」这一步。让候选保持原话，等于把不可信环节压缩到零。

**为什么以 cwd 为隔离边界？** 记忆的作用域就是项目的作用域。跨项目汇总会重新引入「这条事实属于哪个项目」的歧义，而这正是本插件要消除的东西。

## 6. 失败模式与防护

| 失败模式 | 现有防护 | 残余风险 |
| --- | --- | --- |
| 模型把中间结论当真事实 | 代码中无写入路径；候选需人工并入 | 人会误批——但至少错误留在 Git 历史里可回滚 |
| 记忆文件膨胀挤占上下文 | `maxChars` 截断并显式标注 | 截断处的内容会缺失，需要人定期瘦身 |
| 记忆文件读到工作区外 | `memoryPath` 相对路径校验，越界即抛错 | 无（测试覆盖该分支的错误信息） |
| 候选文件无限增长 | `maxCandidates`、`maxCandidateChars` 双上限 | 达到上限后静默不写，需要人清理 |
| 自我污染（把注入内容当用户输入） | 只采 `source.kind === 'user'` 的事件 | 无（测试用插件来源消息做了反例断言） |

## 7. 明确不做的事

以下方向被有意排除，不属于待办清单：

- 语义检索与 embedding 索引
- 模型自动摘要、自动合并、自动删除
- 跨项目或全局记忆库
- 记忆压缩与分片
- 候选文件的自动清理
