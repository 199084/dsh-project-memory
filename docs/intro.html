让模型记住你的项目，

dsh-project-memory 把一份手写的 MEMORY.md 当作唯一事实来源： 注入时带来源路径与修改时间，检索只读且带行号，模型可以提议，但不能静默写入。

模型不该自己决定记住什么

让 Agent 自动提炼记忆，短期很方便，长期会积累三种代价。

记忆幻觉

一次推理的中间结论被写成「事实」，下次会话再当真事实引用，错误就此获得权威。

错误扩散

错误进入记忆库后，会被后续每一次注入放大，而且很难定位到底是哪一次写坏的。

无法回溯

向量库和数据库里的记忆没有 diff、没有 blame、没有回滚，评审无从下手。

四条设计原则

记忆不该是黑盒，它应该是一份经得起 Review 的项目资产。

01人类掌控

MEMORY.md 是唯一确定性事实来源。代码里不存在任何写它的路径。

02随仓库版本化

记忆与代码同仓，提交、合并、Review 完全复用 Git 流程。

03显式来源标记

注入带路径与修改时间，检索带行号，消除「这话是谁说的」这类歧义。

04提案式更新

模型发现的约定只沉淀为候选条目，人的审阅是写入的唯一入口。

快速开始

装插件、写记忆、开一个会话，三步跑通。

1 · 安装插件

dsh plugin --profile web add dsh-project-memory

2 · 写一份 MEMORY.md

# Project Memory

## 关键技术决策
- 用 SQLite 而非 Postgres，因为需要完全离线运行。
- 所有发往 API 中转站的请求统一走 failover 调度池。

## 禁忌与红线
- 不要引入云同步。

配置参数

全部参数都有边界校验（schemastery），越界会直接拒绝。

参数取值范围默认值说明
fileName—MEMORY.md工作区根目录下的记忆文件名
candidateFileName—.dsh-memory-candidates.md候选记忆暂存文件名
maxChars500 – 200006000注入上下文的最大字符数，超出即截断并标注
maxMatches1 – 206单次检索返回的最大命中行数
lazyMode—true是否启用候选采集，关闭后完全只读
maxCandidates1 – 10020候选文件内保留的最大条目数
maxCandidateChars1000 – 200006000候选文件的最大字符数，触顶后静默跳过

和别的记忆方案比

它更接近一本随版本管理的项目笔记本，而不是黑盒仓库。

方案行为主要风险
自动记忆数据库Agent 自动提炼并入库过期或错误的「事实」变成看不见的权威
向量记忆按 embedding 相似度召回难以 Review、调试与复现，脱离 Git 历史
仅靠手写指令文件优秀的手写上下文没有检索工具，也没有来源与行号溯源
dsh-project-memory手写 Markdown + 带来源注入 + 行号检索更新必须由人批准——这是设计意图
